## 0. 共用前提

**0.1 动作钩子不来自数据字段。**
`grep -c actionHooks crucible-compiled.mjs` = **0**。钩子只有一个来源：
`CrucibleAction.#prepareHooks(actionId)`（`:19047`）→ `crucible.api.hooks.action[actionId]`（`:19049`），
按 **actionId** 索引、按 `SYSTEM.ACTION_HOOKS` 名单过滤后 `Object.freeze` 挂到 `this.hooks`（`:19023`）。
ember 数据里那 18 条 `"actionHooks": []` 是**系统压根不读的死字段**。
ember 在 `ember.mjs:126744` 用 `Object.assign(crucible.api.hooks[k], v)` 注册了 **43** 个动作钩子。
`crucible.api.hooks` 外层被 `Object.freeze`（`:14044`），但 `.action` / `.talent` 子表是可写普通对象。

> **任何以「数据里没有 actionHooks ⇒ 这个动作没有自动化」为前提的判断都是错的。**

**0.2 `_tests()` 的合并语义是「同名覆盖，其余保留」。**
`_tests()`（`:20220`）= `yield* this.tags.tags(); yield this.hooks;` —— **标签永远在钩子之前**。
本模块的包装 yield 出 `Object.assign({}, own, extra)`：补丁提供哪个键就顶掉 ember 的哪个键。
→ 想**追加**行为就挑一个 ember 没定义的钩子名；想**替换**就必须把原逻辑整段照抄进来。

**0.3 生命周期时序（实测行号）**

| 阶段 | 位置 |
|---|---|
| `_configureUsage()` → `initialize` 钩子 | `:20283` / `:20302` |
| `_prepare()` → `prepare` 钩子 | `:20314` / `:20320` |
| `use()` 克隆并**重跑** prepare | `:19305` |
| `_canUse()` → `canUse` 钩子 | `:19321` / `:20429`（在 prepare **之后**） |
| `_preActivate()` → `preActivate` 钩子 | `:20504`，早于 `#recordEffectEvents()` `:19370` |
| `_roll()` → `roll` 钩子 | `:20519`，**无 hasDice 守卫** |
| `_post()` → `postActivate` 钩子 | `:20531`，无条件执行 |
| `toMessage()` | `:21376` —— 崩在这之前 ⇒ **连聊天卡都不生成、资源一点不扣** |

**0.4 `??=` vs 裸 `=` 决定谁赢，不是优先级。**
`generic.prepare` 用 `this.usage.defenseType ??= "physical"`（`:4319`），
而 `willpower.prepare` 用裸 `=`（`:4534`）。三个防御标签没有 priority 字段、排序时比较得 NaN 不换位，
它们仍然生效**靠的就是这个差异**。不要写「靠 add() 重排优先级」这种注释。

**0.5 按 action id 注入必须加归属判据。** 语料里存在同 id 不同数据的动作：

| action id | A | B |
|---|---|---|
| `steamVent` | Steam Vent（pulse） | **Burnout**（blast, max 15） |
| `lightningBurst` | crucible（pulse, size 15） | ember（blast, max 15） |
| `frenziedClaws` | crucible.playtest（multiple 4） | ember（multiple 3） |

约定：每个钩子体第一行是形状判据（`this.target?.type === …`）或 owner 判据（`this.item?.id`）。

## 1. 副手打击说「前一个动作不是主手打击」

### 判据在哪

`crucible-compiled.mjs:10132`

```js
lastAction.events.find(e => e.type === "strike")?.weapon.system.slot !== SYSTEM.WEAPON.SLOTS.MAINHAND
```

`SLOTS`（`:6670`）= `EITHER:0 / MAINHAND:1 / OFFHAND:2 / TWOHAND:3`。
`e.weapon` 是 `CrucibleItem#snapshot()`（`:7753`）的产物，用 `this.system.toObject()` 取 **_source**。

### 三条成因（初版只写了两条，且成因描述的函数与行号都错了）

**成因 A —— 已装备武器的 `_source.slot` 停在 EITHER。**
根因不是初版写的 `#getAvailableWeaponSlot` 早退，而是：
schema `slot` 的 `initial: 0`（`:44989`）+ `_prepareWeapons`（`:41550` / `:41555`）**只改派生不回写 _source**
+ `snapshot()` 取 _source（weapon 的 `STATEFUL_FIELDS` 含 `"slot"`，`:44973`）。
（初版引用的那道 `if (equipped === item.system.equipped) return` 早退在 **`canEquipItem`（`:38661`）**，
不在 `#getAvailableWeaponSlot`（`:38731`）里，而且它只在「装备状态没变」时早退。）

> **⚠ 初版说「成因 A 在合集数据里不可达」—— 那句是反的，已推翻。**
> 当时的取样只覆盖了顶层 `!items!` / `!actors.items!` 文档，而 `ember.crucible-adventure.json`
> **只有 1 个顶层文档**，把 265 个 actor、473 件武器全嵌在里面。
> 全树重扫：**85 件已装备、非天生、`_source.slot = 0` 的武器，分布在 61 个 actor 上，其中 11 个带 Dual Wield。**
> 复现用例用 **Juro Wandren**（双匕首，两把 `_source.slot` 都是 0），**不要**用 pregen ——
> `crucible.pregens` 的 22 件已装备武器 `_source.slot` 确实全是 1/2/3。

**成因 B —— 工作流问题。** `lastConfirmedAction`（`:36499`）只认 `flags.crucible.confirmed` 为真的聊天卡。

**成因 C（新增，而且是最主的一条）—— 徒手 / 临时武器。**
`UNARMED_DATA`（`:6681`）的 system 里**没有 slot** → `initial: 0`；
unarmed 类目（`:6427`）`hands:1/main:true/off:true` 使 `prepareBaseData`（`:45077`）的兜底也不触发；
`_prepareWeapons` 的 either 桶明确写了 `w.system.slot = MAINHAND/OFFHAND`（`:41550`/`:41555`），
**紧接着的徒手赋值（`:41562`/`:41565`）一个字都不设 slot**；
`_getUnarmedWeapon`（`:41624`）走 `new itemCls(data, {parent})`，**`_id` 为 null**。
于是 snapshot 是 `{_id: null, slot: 0}`。

而系统自己在 `:41606` 明文把全徒手判为双持（`weapons.dualWield = weapons.unarmed || …`），
Flurry / Dervish / Feinting Strike 赤手空拳全都能用，**唯独 Dual Wield 自己那条不行**。

### 本模块的做法

P1 放宽判据（回查活武器的派生 slot、任意一次 strike 命中主手即通过），
N8 用 `updateSource` 给**没有 `_id`** 的徒手/临时武器补上手位（纯内存实例，不落库；
系统自己在 `:18286` 就是这个用法）。两者互补 —— 成因 C 下 P1 的三级判据全部落空。

### 顺手记给 crucible 的

`offhandStrike.canUse`（`:10131`）是七个读 `lastConfirmedAction` 的钩子里**唯一不加 `?.`** 的
（对照 `:3733` / `:9288` / `:9703` / `:10986` / `:11053` / `:11225` / `:12541`），
当前被 `afterStrike` 标签挡住不可达。

## 2. 凯思族「撕咬」的范围

`ember.crucible-character` → `!items!emberKethLineage` 的内嵌动作 `suddenBite`：

```json
"range": { "minimum": 2, "maximum": 2, "weapon": false },
"target": { "type": "single", "number": 1, "scope": 3 }
```

`minimum` 量的是**贴边距离**（`getLinearRange`，`:32158`，相邻两个 token 是 0），
所以 `min: 2` 把「贴着咬」排除掉，`max: 2` 又把远的排除掉 —— 在 5 尺格场景上**这个动作永远无法生效**。

| 动作 | 目标类型 | range |
|---|---|---|
| `Rune: Storm > Energize` | single | `min: null, max: 1` |
| `Heart Attunement > Spark of Ember` | single | `min: null, max: 1` |
| `Drakon Lineage > Drakonfire` | cone | `min: 8, max: 8` |
| **`Keth Lineage > Sudden Bite`** | **single** | **`min: 2, max: 2`** |

> **⚠ 初版给 Drakonfire 那一行的注解「锥形的 min=max 是锥长的写法」是错的。**
> 不存在这种写法 —— 锥长只取 `maximum`（或 `target.size`），`:2865` + `:2893` 全程不碰 `range.minimum`。
> `range.minimum` 只有三个消费点：`:19692`（**仅 single**）、`:20190`（`_getWeaponAvailability`，读 _source）、
> `:3054`（**仅 movement**）。cone 根本不读它，那一行的 `min: 8` 是惰性冗余值。

**补丁纪律**：`_getWeaponAvailability`（`:20187`）的 `min` 无条件读 `_source.range.minimum`，
`max` 却按 `range.weapon` 在 _source 与派生之间切换 —— 在 `prepare()` 里改 `this.range` 的补丁，
只在动作**不带** strike/reload 标签时完整生效。P2 不受影响；
以后给 `ferociousLeap` / `flyingKick` 之类打 range 补丁必须同时改 `_source`。

## 3. 带 rune 的天赋漏了该符文的小戏法与训练等级

### 机制

`system.rune` 只负责把符文塞进 `grimoire.runeIds`（`:41287`）；
每个符文的**招牌小戏法**挂在 crucible 那条 `Rune: X` 天赋的 `system.actions` 上。
crucible 自带的 12 条 `Rune: X` **每一条**都带一个小戏法。

### 两批受害者

**(a) ember 的四个血统**

| 血统 | rune | training | 缺的小戏法 |
|---|---|---|---|
| Zeph 泽夫 | storm | `{storm, 1}` ✅ | `energize` |
| Drakon 德拉肯 | flame | `{"", null}` ❌ | `enkindle` |
| Kiska 基斯卡 | illusion | `{"", null}` ❌ | `seeming` |
| Nir'ae 尼尔艾 | illumination | `{"", null}` ❌ | `reveal` |

**(b) `crucible.summons` 里 9 条旧快照（新增，crucible 侧）**

火/霜/土/风暴精怪与访客、Moldy Skeleton 随身的 `Rune: X`：
`system.training` 全是 `{type:"", rank:null}`、`system.actions` 全是 `[]`，
其中 4 条还是已废弃的小写 id（`runeflame0000000` 等）。actor 的 `_stats.systemVersion` 停在 **0.9.0**。

后果之二：`#prepareTalents` `:41281` `if (training.type) {` —— 空串直接跳过，
`system.training.<rune>` 压根不存在，但 `:41287` 仍 push 进 `grimoire.runeIds`，
所以精怪**能施法、只是未受训** → `getSkillBonus`（`:36647`）落到 `untrained.bonus = -4`（`:6834`）。
反证：`crucible.pregens` 里 27 条同类内嵌副本全部带 `{type, rank:1}` + 对应小戏法。

> 缺陷窗口：`_performMigrations` `:47884` → `syncTalents()` `:38023` 会在**下一次系统版本迁移**时自动修好
> （`TALENT_ID_MIGRATIONS` `:6877` 恰好收录了那 4 个小写 id）。但合集本身永不修复，每个新世界都会踩一次。

### 本模块的做法

按 **rune** 查表（不是按天赋 item id），一次盖住两批。
`life`(Healer) / `soul`(bard) 故意不在表里 —— 它们的**正版条目**训练等级本来就是空的，属于设计而非旧快照。

## 4. 「疗愈导流」 —— ⚠ 本节初版整节错误，已撤回重写

### 初版错在哪

初版判定「这个动作缺 `generic`/`healing`、且带着会把恢复归零的 `harmless`，所以什么都不发生」，
依据是数据里**没有 `actionHooks` 这个键**。这个依据本身就是错的（§0.1）—— 系统压根不读那个字段。

**ember 在 `ember.mjs:125213-125233` 注册了完整的三个钩子**：

```js
HOOKS$4.mayisRestorativeRedirection = {
  canUse() { /* 校验「上一动作是被 RESIST 的法术」，并设 this.usage.resource */ },
  initialize() { this.usage.bonuses.ability = this.actor.getAbilityBonus(["wisdom","presence","intellect"], {type:"best"}); },
  postActivate() { /* recordEvent({target, resources:[{resource, delta: max(2*ability + damageBonus, 0)}]}) */ }
};
```

逐条订正：

| 初版说法 | 实情 |
|---|---|
| 「没有 generic ⇒ hasDice 恒 false ⇒ 不掷骰 ⇒ 什么都不发生」 | **不掷骰不是缺陷，是正典写法。** 无骰恢复（postActivate 记 resources 事件）在 crucible 自家有 11 条先例：`secondWind`(`:10711`，还显式 `hasDice = false`)、`rallyingCry`(`:10257`)、`fontOfLife`(`:9547`)、`healingElixir`(`:9671`)、`lastStand`(`:9830`)…… 全是 healing/rallying + 零 generic |
| 「`healing`/`rallying` 缺失 ⇒ hasDice 为 false」 | 反了：这两个标签的 `prepare` **自己就设 `hasDice = true`**（`:4544`/`:4557`）却**没有 `roll()``。而 hasDice 的消费者只有三处（`:2511` 对话框上下文、`:13607`、`:37109`），对普通动作**只影响对话框显不显示骰子区** |
| 「`harmless` 会把恢复归零」 | **不会。** `harmless.postActivate`（`:4453`）只动 `event.roll?.hasDamage` 的骰子；resources 事件不是 roll。crucible 自家的 `revive`（`:10620`）甚至**主动调用**它再发放恢复。全库带 harmless 的动作 96 条 |
| 「这是一整类」那张表 | 重写：`mayisRestorationOfTheDeep`（`:125237`）本来就是好的**且根本不带 harmless**；`akonForesight`（`:125195`）的自动化也是好的，只是 `healing` 标签名不副实（它恢复的是 Focus）—— 降级为冗余标签，不是缺陷 |

### 初版补丁造成的实际损害

`Object.assign({}, own, extra)` 只顶掉 `initialize`/`prepare`，**ember 的 `canUse` 与 `postActivate` 原样保留**：

1. 补丁加的 `generic` → `generic.roll()`（`:4323`）对**队友**掷一次 `dc: target.defenses.wounds.total`
   的 AttackRoll —— 聊天卡上多一条打友军的攻击骰，还可能 Resist。**无条件发生。**
2. ember 的 postActivate 照跑 → 同一次动作产生**两笔**恢复事件（`recordEvent` `:19192` 是 push，
   `"strike"` 不在 `#SINGLETON_EVENT_TYPES` 里）。第二笔要掷骰 ≥GLANCE 且 overflow>6 才 >0，
   所以是**加算、偶发**，不是稳定翻倍。
3. `resolveRedirectResource` 是死代码：补丁在 `prepare` 设 `usage.resource`，
   ember 的 `canUse` 在 prepare **之后**跑（§0.3），必被覆写。

### 真正剩下的唯一缺陷

`ember.mjs:125221`：

```js
this.usage.resource = lastAction.damage?.resource ?? "health";
```

`CrucibleSpellAction.#prepareDamage`（`:21884`）产出的对象是
`{base, bonus, multiplier, type, restoration}` —— **没有 `resource` 键**，所以表达式**恒为 `"health"`**。
真值在那次被抵抗的骰子里：`AttackRoll#resolveDamage`（`:3291`）把 `resource` 显式写进 `data.damage`
（未命中/RESIST 同样写满，只是 total=0），法术侧来源是 `spellAttack` `:37130`
`resource: options.resource || spell.rune.resource`。会打士气的符文确实存在（control `:5792`、illusion `:5859`）。

**新补丁只覆盖 `canUse`**：先调 ember 的原实现（复用它的全部校验、让它照常 throw），再改 `usage.resource`。

### 附带订正：序列化事件的字段名

聊天卡 flags 里骰子下标的键名是 **`rollIndex`**
（`CrucibleActionEvent#toObject` `:18296` 写 `obj.rollIndex = this.roll.data.index`，`fromObject` `:18327` 读回），
**没有 `roll` 这个键**。初版的 auto 档读 `ev.roll`，因此 100% 失效且静默退回 health。

## 6. 已排除 —— 不要重复报

1. **「ember 21 条 `{turns:N}` 效果时长被 v14 丢弃 ⇒ 状态变永久」** —— `CrucibleAction.migrateData`（`:21573`）
   会调核心 `ActiveEffect.migrateData` 把 `{turns:6}` 迁成 `{value:6, units:"turns"}`，迁移在 clean 剪枝之前。
   真正的问题是 `units:"turns"` 会被 `CrucibleActiveEffect._preCreate`（`:39581`）**主动拒绝创建** ——
   那是**另一族**缺陷（效果不生成，不是永久），修法完全不同。
2. **「Wirrun『不懈猎手』的 `range.minimum:1` 是缺陷」** —— crucible 自己的 `SPELL.GESTURES.arrow`（`:5930`）
   range 块与它逐字节相同；schema `min:1`（`:18605`）本身就是「有最小射程」的规范写法。与 P2 不是同一类。
3. **「豪勇之笛 target 写错方向」** —— `effects: []` + 无钩子，什么都不会发生；
   `single`/`scope:4` 全是 schema 默认值，同包 13 件带「Under Development」横幅的物品里 5 件字段完全一致。
4. **「ember 16 个文化里 8 个不给天赋」** —— `crucible-async.mjs:246` 的建卡向导用 `system.item` 当开关，
   非 null 的恰好就是那 8 个；另外的玩家**根本选不到**。
5. **「P1 成因 A 无数据支持」** —— 反被推翻，见 §1 的加框说明。
6. **`akonForesight` 的 `healing`+`harmless`** —— 与 crucible 自家 `antitoxin`/`healingElixir`/`oozeMultiply`
   写法完全一致，无运行时后果，最多算冗余标签。
7. **`auraSlipstream` 的数值 `mode:`（`ember.mjs:125459`）** —— 位置写对了（在 `system.changes` 下），
   `mode` 是野键被 schema 清掉、`type` 落 `initial:"add"`，而作者要的正是 ADD。**当前行为完全正确。**

## 建议上报给谁

**Crucible（foundryvtt/crucible）**

1. `CrucibleItem#snapshot()` 取 `_source`，而武器手位对 slot=EITHER 的武器只存在于派生值里；
   **徒手武器从头到尾没被赋过手位**（`:41562`/`:41565`），且 `_id` 为 null。
   凡是读 `e.weapon.system.slot` 或 `items.get(e.weapon._id)` 的钩子都受影响。
2. `crucible.summons` 的 9 条 `Rune: X` 是 0.9.0 的旧快照（无训练等级、无小戏法、4 条是废弃小写 id）。
3. `syncTalents` 的空值判断、`resetAllActorTalents` 的数组调 Set 方法、
   `#acquireTargetsFromRegion` 的空集语义、`swallow` 的 17 字符 `_id`、
   `ActionEffect` typedef 仍写着顶层 `changes`（**这条很可能是 ember N2 的来源**）、
   `offhandStrike.canUse` 缺 `?.`。

**Ember（Mage Hand Press）**

1. `Keth Lineage > suddenBite` 把 `min: 2` 写在 single 目标上，贴身攻击不可能命中。
2. 四个给 rune 的血统都漏了该符文的招牌小戏法；其中三个还漏了 `training` 等级。
3. `abyssMarkUnmaking` 的效果 id 只有 15 字符 → 整个动作抛异常中止（6 处出现）。
4. `sentinelShielding` / `tyraphicTransformation` 的 `changes` 写在 effect 顶层而非 `effect.system` 下。
5. `sentinelKick` 的 duration 有 value 没 units → staggered 变永久。
6. `heartSparkOfEmber` 的 scope 与它的复活分支矛盾。
7. `bewilderingGaze` 缺 `willpower`；`antigravityStone` 的 target 没填；`darkflameCirclet` 该用 `spell` 而非 `composed`。
8. `mayisRestorativeRedirection` 读 `lastAction.damage.resource` —— 法术动作上没有这个字段，恒为 health。
